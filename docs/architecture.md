# Архитектура

`lzt_eventus_sdk` вырастает из «REST-клиента + верификатора подписи вебхуков» в небольшой
aiogram-style фреймворк-потребитель событий: один `Dispatcher`, питаемый четырьмя подключаемыми
транспортами (polling, webhook, SSE, WS), вложенное дерево `Router`, внешне-внутренняя цепочка
middleware и generic K/V-хранилище для дедупа + возобновляемых курсоров — без зависимости от
приватных библиотек `evented`/`wsflow` и без их вендоринга. Та же форма, но в масштабе этого SDK.

```
management API (lzt-eventus)
        │
        ▼
   ┌─────────┐   normalize wire frame    ┌────────────┐    feed(event, ctx)   ┌──────────────┐
   │ sources/ │ ─────────────────────▶  │ ClientEvent │ ──────────────────▶  │  Dispatcher   │
   │ polling  │                          └────────────┘                       │  + Router     │
   │ webhook  │                                                                │  + middleware │
   │ sse / ws │                                                                └───────┬───────┘
   └─────────┘                                                                          │
                                                                                          ▼
                                                                                     your handlers
```

## 1. Модель события — обобщённое событие, опциональный типизированный реестр

Каталог `EventType` на сервере открыт и растёт. Закрытая клиентская иерархия
подкласс-на-каждый-тип упала бы на любом типе события, который сервер добавит раньше, чем SDK
его догонит. Вместо этого: диспетчеризация ключуется по **строке** `event_type` (aiogram
ключуется по типу апдейта точно так же); базовый класс `ClientEvent` несёт `seq`/`event_type`/
`data`/метаданные; потребители, которым нужна типизация, регистрируют модель полезной нагрузки в
`PayloadRegistry` (`events.register("new_lot")`), она резолвится лениво. Неизвестный тип падает
обратно на базовый `ClientEvent`, а не в ошибку — обратная совместимость важнее исчерпывающей
типизации.

## 2. Единая точка входа `Dispatcher.feed()` — транспорты — тупые источники

Каждый транспорт нормализует свой wire-фрейм в `ClientEvent` и вызывает *один и тот же*
`Dispatcher.feed(event, ctx)`. Отдельного пути диспетчеризации на каждый транспорт нет — хендлер,
зарегистрированный один раз, получает события независимо от того, какой транспорт их доставил.
Транспорты различаются только способом получения события и семантикой ack (§4).

## 3. Мультиаккаунт — общий Dispatcher, контекст инжектится по аккаунту

Одно дерево `Router` и одна цепочка middleware общие для всех аккаунтов. Каждый источник
привязан к `AccountContext` (`ManagementClient` + `subscription_id` + label + креды стрима). При
`feed` этот контекст инжектится в словарь `data` middleware, так что хендлер читает
`data["client"]` (клиент нужного аккаунта — например, чтобы вызвать `confirm_read`) и
`data["subscription_id"]`. Это тот же паттерн, что инжекция `bot` в aiogram.

## 4. Транспорты (`sources/`)

| Источник | Требует | Ack / возобновление |
|---|---|---|
| `PollingSource` | только `httpx`, переиспользует существующий REST-клиент | `confirm_read(up_to_seq)` после успешной диспетчеризации |
| `SSESource` | стриминг `httpx` | возобновление через `Last-Event-ID` через `CursorStore` |
| `WSSource` (extra `[ws]`) | `websockets` | Auth-фрейм `{subscription_id, token, last_seq}`, возобновление с `last_seq` |
| `WebhookReceiver` (`server/`) | чистый ASGI, без зависимости от фреймворка | серверный retry-контракт (ниже) |

Все четыре работают под `SourceSupervisor` — рестарт с backoff при сбое, так что один
нестабильный транспорт не роняет весь процесс.

**Вебхук-приёмник — чистый ASGI намеренно.** Затягивание FastAPI/Starlette притащило бы веб-
фреймворк в клиентскую библиотеку. Чисто-ASGI callable — это пара десятков строк, без новых
зависимостей, сохраняет `pip install lzt-eventus-sdk` httpx-only, и при этом естественно
монтируется в любое приложение FastAPI/Starlette через `app.mount(...)`.

**Политика ошибок/ack зависит от источника и привязана к retry-контракту сервера.** Серверная
доставка вебхуков считает 5xx/408/429 повторяемыми, а прочие 4xx — терминальными. Поэтому
`ErrorBoundaryMiddleware` мапит исключение хендлера на источнике **webhook** в `503` (сервер
передоставит; дедуп идемпотентности защищает от двойной обработки); на **SSE/WS/polling** —
логирует и не продвигает курсор дальше упавшего `seq` (переотдаётся при переподключении/следующем
поллинге). Плохая подпись — это `401` (терминально, самоисцеления не бывает); битое тело — `400`
(терминально); попадание в дедуп — `200`.

## 5. Хранилище — два фасада над одним `BaseStorage[K, V]`

Ключи дедупа и возобновляемые курсоры `last_seq` — это оба K/V. `IdempotencyStore` и
`CursorStore` — тонкие фасады над одним ABC `BaseStorage[K, V]` (`MemoryStorage` идёт как
дефолт), так что один будущий бэкенд обслуживает оба. Форма курсора зеркалит собственное
курсорное хранилище сервера (`last_seq` на потребителя), но остаётся локальной для клиента —
рестарт возобновляет SSE/WS/polling с того места, где остановились.

## 6. Middleware (`middleware/`)

Внешне-внутренняя цепочка, той же формы, что и transport middleware на стороне сервера:
`LoggingMiddleware`, `ErrorBoundaryMiddleware` (политика ack из §4), `IdempotencyMiddleware`
(дедуп через `IdempotencyStore` до того, как хендлер вообще запустится).

## 7. Аварийный выход — обход Dispatcher целиком

Каждый `BaseSource` предоставляет `stream()` — сырой итератор `async for event in
source.stream()`, полностью пропускающий роутинг. Потребитель, который не доверяет фреймворку,
может вручную водить события, всё ещё переиспользуя механизм переподключения/курсоров;
`Dispatcher.feed()` — это просто дефолтный потребитель `stream()`.

## Структура пакета / зависимостей (extras)

| Установка | Добавляет зависимость | Даёт |
|---|---|---|
| `lzt-eventus-sdk` (базовый) | только `httpx` | REST-клиент, подпись, события, диспетчеризация, middleware, in-memory хранилище, polling-источник, SSE-источник (стриминг httpx), вебхук-приёмник (чистый ASGI) |
| `lzt-eventus-sdk[ws]` | `websockets>=12` | `WSSource` (у httpx нет WS-клиента) |

SSE и вебхук-приёмник не требуют новых зависимостей (httpx умеет стриминг; чисто-ASGI
монтируется в собственный сервер потребителя) — WebSockets единственный транспорт, который
вынуждает добавить зависимость, поэтому это единственный обязательный extra.

## Имена паттернов

Router-дерево + Observer (диспетчеризация) · Chain-of-Responsibility (middleware) · Adapter
(каждый источник нормализует свою wire-форму) · Supervisor + retry-with-backoff
(`SourceSupervisor`) · Idempotency-Key дедуп · Resumable-Cursor (чекпоинт) · Strategy (ack-
политика в зависимости от источника).
